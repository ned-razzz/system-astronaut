# 사용자 피드백으로 정리한 시퀀스 다이어그램 작성 원칙

작성일: 2026-09-30  
목적: system-astronaut 상세 설계 스킬의 시퀀스 다이어그램 작성 규칙에 사용할 사례 기록  
대상: [sequence_diagram.md](../detailed_design/sequence_diagram.md)

이 기록은 세 차례 사용자 피드백에 대해 무엇이 문제였고, 어떻게 수정했으며,
그 과정에서 어떤 시퀀스 다이어그램 작성 원칙을 도출했는지 정리한다.
핵심은 **완결되는 작업 단위로 나누고, 핵심 모듈 사이의 흐름을 보여 주며,
추상화한 뒤에도 시작부터 결과까지 인과 관계를 이어 주는 것**이다.
아래 원칙은 이 사례에서 도출한 스킬 규칙 후보이며 아직 스킬에 적용한 것은 아니다.

## 1. 피드백과 수정의 전체 흐름

| 단계 | 사용자 피드백 | 수정 | 도출한 원칙 |
| --- | --- | --- | --- |
| 첫 작성 후 | 기능을 하나의 다이어그램에 전부 표현하려 하니 너무 복잡하다. | 큰 그림 3개를 완결되는 작업 단위 9개로 분리했다. | 하나의 시퀀스는 시작과 결과가 있는 작업 하나를 다룬다. |
| 작업 분리 후 | 모듈을 연결하는 PipelineRuntime은 전체 흐름을 파악할 때 빠져도 된다. | 조율자를 생략하고 핵심 모듈 사이의 논리적 인계를 표시했다. | 서비스 흐름을 설명하는 데 필요한 참여자만 남긴다. |
| 조율자 생략 후 | 대피 다이어그램이 끊겨서 흐름이 보이지 않는다. | 시작 사유, 실행 결과, 새 관측, 종료 처리를 메시지로 연결했다. | 추상화하더라도 다음 단계가 왜 시작되는지는 보여 준다. |

이 수정들은 서로 연결된다. 작업을 나누기만 하면 조율자 왕복이 남고,
조율자를 지우기만 하면 작업의 연결 근거가 사라질 수 있다.
따라서 작업 경계, 참여자 선택, 메시지의 인과 관계를 함께 검토해야 한다.

## 2. 첫 번째 피드백: 완결되는 작업 단위로 나눈다

### 사용자 피드백

> 각 기능을 하나의 다이어그램에 전부 표현하려 하니까 너무 복잡해졌어.
> 적당히 완결되는 작업 단위로 다어이그램을 분리해.

### 수정 전의 문제

시작 검증과 자동사냥, 재관찰과 대피, 후속 성장과 모니터링을 각각 큰 그림으로 묶었다.
한 그림에 참여자와 중첩 분기가 많았으며, 목적이 다른 작업도 함께 들어 있었다.
읽는 사람이 현재 작업의 시작, 완료 조건, 다음 작업으로의 인계를 구별하기 어려웠다.

### 실제 수정

다음 작업 단위로 분리했다.

| 작업 | 범위 |
| --- | --- |
| 시작 조건 검증 | 시작 요청 → 실행 허용 또는 거절 |
| 자동사냥 한 주기 | 화면 관측 → 목표·명령 결정 → 입력 실행 |
| 위치 재관찰 | 위치 실패 → 회복 또는 중단 결정 |
| HP·MP 재관찰 | 자원 실패 → 회복·위치 재관찰·대피로 인계 |
| 지정 안전 지점 대피 | 대피 필요 → 이동·도착 확인 또는 실패 → 입력 해제·기록 |
| 실행 종료 | 중단 요청·결정 → 입력 해제·기록 → 종료 |
| 후속 캐릭터 생성 | 생성 요청 → 결과 확인 → 성장 절차 인계 또는 중단 |
| 후속 성장 단계 전환 | 성장 기준 충족 → 현재 사냥 종료 → 성장 절차 → 다음 사냥 시작 |
| 후속 PC 상태 조회 | 조회 요청 → 상태 수집 → 표시 |

대피 종료까지 펼친 범위는 이후 세 번째 피드백에서 보완한 최종 형태다.
다이어그램 수 9개는 이 프로젝트의 결과이며 스킬의 고정 출력 개수가 아니다.

### 작성 원칙

분할 기준은 SR 번호나 문서 길이가 아니라 **작업의 시작 사건과 결과**다.
한 그림이 여러 독립 작업을 다루면 분리하고, 분리한 그림마다 결과 또는 인계 지점을 남긴다.
메시지 몇 개마다 쪼개어 작업 전체를 읽을 수 없게 만드는 것도 피한다.

작성 전에 각 그림에 대해 다음 한 문장을 채운다.

“이 작업은 ___에서 시작하고, ___을 수행하여, ___ 결과를 내거나 ___ 작업에 인계한다.”

이 문장을 여러 독립 목적의 나열로만 쓸 수 있다면 분할 범위를 다시 검토한다.

## 3. 두 번째 피드백: 핵심 흐름에 필요한 참여자만 남긴다

### 사용자 피드백

> pipelineruntime은 composition of root로 모듈끼리 연결시켜주는 역할이라
> sequence diagram에서 전체 흐름을 파악하는데는 빠져도 될 것 같은데.

### 수정 전의 문제

작업을 나눈 뒤에도 화면·상태·목표·명령이 모두 PipelineRuntime을 왕복했다.
그 결과 핵심 모듈 사이에 어떤 데이터가 어떤 순서로 전달되는지가 간접적으로 보였다.
모듈 호출을 연결하는 구현 구조가 서비스 흐름보다 더 눈에 띄었다.

### 실제 수정

모든 시퀀스에서 PipelineRuntime 참여자를 생략하고 핵심 흐름을 직접 표시했다.

```text
수정 전:
PipelineRuntime → ScreenCapture → PipelineRuntime
PipelineRuntime → StateRecognizer → PipelineRuntime
PipelineRuntime → GoalPolicy → PipelineRuntime
PipelineRuntime → InputPolicy → PipelineRuntime
PipelineRuntime → InputController

수정 후의 논리적 흐름:
ScreenCapture → StateRecognizer → GoalPolicy → InputPolicy → InputController
```

화살표는 실행 조율을 생략한 데이터 전달과 작업 인계라고 문서에 명시했다.
실제 직접 호출을 강제하는 표현으로 해석하지 않도록, 구성·연결 관계는
[클래스 다이어그램](../detailed_design/class_diagram.md)을 참조하게 했다.

### 작성 원칙

참여자는 코드에 존재한다는 이유보다 **그 작업을 이해하는 데 필요한 책임을 갖는가**로
선택한다. 연결·조율 담당자와 세부 DTO가 핵심 흐름을 가리면 생략할 수 있다.

생략은 표현의 추상화다. 조율자를 지운 뒤 모든 호출을 다른 정책 모듈에 옮겨서,
그 정책이 실행 관리까지 책임지는 것처럼 보이게 하면 안 된다.
판단·행동 계획·입력 실행의 책임 경계를 유지하고 그림의 추상화 수준을 설명한다.

현재 클래스 설계의 PipelineRuntime에는 주기 실행·취소 등 조율 책임도 있다.
이번 피드백으로 그 책임을 제거하거나 아키텍처를 변경한 것은 아니다.
정확한 호출 구조를 검토하는 그림이 필요하면 조율자를 다시 포함할 수 있다.

## 4. 세 번째 피드백: 추상화해도 흐름은 끊기지 않아야 한다

### 사용자 피드백

> 지정 안전 지점 대피 다이어그램이 뚝뚝 끊기도 흐름이 안보이는데?

### 수정 전의 문제

대피 시작은 주석으로만 적었고, 종료도 공통 중단 작업으로 인계한다는 주석으로 끝냈다.
이동 명령 뒤에는 새 화면 획득이나 입력 실행 결과 없이 인식 결과가 나타났다.
단계는 존재했지만 다음 단계로 넘어가는 데이터와 계기가 생략되어 있었다.

```text
대피 필요라는 주석
→ GoalPolicy 내부 판단
→ 이동 명령
→ 갑자기 나타나는 위치 관측
→ 중단 작업 인계라는 주석
```

### 실제 수정

대피 사유를 인식 모듈이 목표 정책에 전달하는 메시지로 표현했다.
이전 입력 해제와 계획 초기화도 메시지로 나타냈다.
이동 명령의 실행 결과를 받은 뒤 새 화면을 얻고, 위치·경로·도착 여부를 인식하여
다음 이동 판단에 전달하도록 연결했다.

```text
상태 인식 결과와 대피 사유 전달
→ 대피 필요 판단
→ 기존 입력 해제와 계획 초기화
→ 현재 위치·경로·도착 여부 판단
→ 이동 목표 전달
→ 이동 키 입력
→ 입력 실행 결과
→ 새 화면 획득
→ 위치·경로·도착 인식
→ 계속 이동 또는 종료 판단
→ 입력 해제와 계획 종료
→ 중단 결과 기록과 알림
```

도착, 시간 초과, 위치·경로 판단 상실은 공통 종료 처리로 합류하게 했다.
공통 종료 다이어그램이 따로 있어도 대피 작업의 결과를 이해하는 데 필요한 입력 해제와
기록은 대피 그림에도 펼쳤다. 캡처 요청 등 화살표는 논리적 인계라는 설명도 유지했다.

### 작성 원칙

생략할 수 있는 것은 반복되는 구현 세부이며, **작업을 이어 주는 원인과 결과**는 남긴다.
특히 다음 세 연결은 메시지로 확인할 수 있어야 한다.

- 어떤 사건이나 관측 때문에 작업이 시작되는가?
- 실행 후 무엇으로 결과를 확인하며, 그 결과가 다음 판단으로 어떻게 돌아가는가?
- 성공·실패·시간 초과 시 무엇을 수행하고 어떤 결과로 끝나는가?

주석은 조건과 배경을 보충한다. 핵심 처리 대신 “수행함”, “종료함”이라고만 적으면
다이어그램의 흐름이 끊길 수 있다. 반대로 흐름에 필요하지 않은 부수 작업까지
모두 메시지로 넣으면 첫 번째 피드백의 복잡도 문제로 돌아간다.

제어 작업에서는 `관측 → 판단 → 명령 → 실행 → 새 관측 → 다음 판단`의 반복이 보여야 한다.
입력 전송 성공과 게임 내 이동·도착 성공은 구분하고 반복 종료 조건을 적는다.

## 5. 상세 설계 스킬에 적용할 작성 절차

다음 절차는 위 피드백에서 도출한 제안이다.

1. **그림의 목적을 정한다.** 서비스의 논리적 흐름을 설명하는지, 실제 호출 구조를
   검토하는지 먼저 명시한다. 이 사례는 서비스 흐름 이해가 목적이다.
2. **작업 경계를 정한다.** 시작 사건, 주요 처리, 결과와 인계 대상을 한 문장으로 쓴다.
   독립적인 작업이면 별도 그림으로 나눈다.
3. **필요한 참여자를 고른다.** 핵심 판단·계획·실행 책임을 남기고 연결 조율과 세부
   데이터 구조는 흐름을 가릴 때 생략한다. 생략한 호출의 의미를 문서에 설명한다.
4. **주 흐름부터 연결한다.** 각 메시지에 전달 데이터 또는 요청할 작업을 적는다.
   앞 단계 결과가 다음 단계의 입력이 되는지 위에서 아래로 따라 읽는다.
5. **결과 확인과 반복을 연결한다.** 실행 결과와 실제 관측을 구분하고, 관측이 다음
   판단에 돌아오는 경로 및 반복 종료 조건을 표시한다.
6. **예외를 완료 지점에 연결한다.** 판단 불가·실패·시간 초과도 결과 또는 다음 작업으로
   이어지게 한다. 작업 완결에 필요한 종료 처리는 공통 작업이 있어도 펼칠 수 있다.
7. **복잡도와 단절을 함께 검토한다.** 그림이 커졌으면 작업을 분리하고, 흐름이 끊겼으면
   필요한 메시지를 복원한다. 메시지 수를 줄이는 것만으로 가독성을 판단하지 않는다.

SR은 조건·시간 제한·종료 결과의 기준으로 사용한다. 이 사례의 5초·30초나 모듈 이름을
스킬의 보편적인 기본값으로 만들지 않는다. 미확정 정책은 임의로 확정하지 않는다.

## 6. 리뷰에서 확인할 질문

- 그림마다 시작 사건과 완료 결과 또는 다음 작업의 인계가 보이는가?
- 서로 독립적인 목적을 한 그림에 묶지 않았는가?
- 연결 담당자를 왕복하는 메시지가 핵심 모듈의 흐름을 가리지 않는가?
- 논리적 인계인지 실제 호출인지 설명되어 있으며 모듈 책임을 오해하게 만들지 않는가?
- 위에서 아래로 읽을 때 다음 메시지가 왜 발생하는지 앞 메시지로 설명할 수 있는가?
- 실행 후 결과 확인이 보이며 그 관측이 다음 판단으로 이어지는가?
- 성공·실패·시간 초과가 모두 종료 처리나 다른 작업으로 연결되는가?
- 주석에만 적힌 시작·실행·종료 중 메시지로 복원해야 할 부분은 없는가?
- 생략한 세부를 복원하지 않아도 작업 하나를 끝까지 설명할 수 있는가?

## 7. 자료와 확인 범위

최상위 기준은 [시스템 요구사항](../architecture_design/system_requirements.md)이며,
초기 표현은 [Bubembe 상세 설계](../../../bubembe/doc/detailed%20design/sequence_diagram.md)를
참고했다. 전체 설계 산출물 소개와 게임별 설정값 설명은 이 기록의 중심에서 제외했다.

문서 내용과 Mermaid 코드 블록의 종료 균형, 런타임 참여자 생략 여부를 확인했다.
Mermaid 렌더러를 통한 화면 검증이나 게임 실행 시험은 수행하지 않았다.
사용자 피드백과 그에 따른 수정은 기록된 사실이고, 위 작성 절차와 검토 질문은
스킬 구현에 활용할 제안이다.
