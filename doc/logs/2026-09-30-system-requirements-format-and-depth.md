# 시스템 요구사항의 Sub-SR 형식과 depth 개선 기록

작성일: 2026-09-30  
대상: [시스템 요구사항](../architecture_design/system_requirements.md)  
목적: system-astronaut의 요구사항 작성·검토 규칙을 개선하기 위한 사례 기록

이번 변경은 두 가지 문제를 다룬다. 첫째, Sub-SR의 번호·이름·설명을 한 셀에
넣던 형식을 분리해 각 항목의 역할을 명확히 했다. 둘째, 최상위 기능 SR을
사용자에게 제공하는 완결된 기능 단위로 맞추고, 그 기능을 구성하는 동작을
Sub-SR로 통합했다. 형식 변경은 표의 표현을, depth 변경은 요구사항의 묶음과
상하 관계를 개선한다.

## 1. 확인한 문제와 변경 근거

사용자는 자동사냥을 하나의 요구사항으로 다루면서 자동 성장의 캐릭터 생성,
사냥터 이동, 퀘스트 진행을 각각 최상위 요구사항으로 정의하면 depth가 맞지
않는다고 지적했다. 수정 전 문서에서는 자동사냥도 사냥터 선택·상황 파악,
사냥 동작, 문제 복귀로 나뉘어 있었다. 따라서 자동 성장만 묶으면 최상위
요구사항의 수준이 여전히 달라진다.

변경 전후는 Git HEAD와 현재 문서의 차이로 확인했다. depth 조정 직전의
문서에는 이미 `No.`, `Function name`, `Function description`을 분리한 표가
있었다. 이번 조정에서는 `No.`를 `Sub-SR`로 바꾸고 그 형식을 유지했다.
이 기록은 확인 가능한 형식의 변화를 함께 정리하며, 앞선 형식 변경의 별도
요청 내용이나 수행 시점은 추정하지 않는다.

## 2. Sub-SR 표 형식 변경

### 변경 전후

Git HEAD의 표는 다음 세 열을 사용했다.

```markdown
| Sub-SR and scope | Condition | System behavior and result |
|---|---|---|
| 01 — 사냥 이동: 몬스터를 사냥할 위치로 캐릭터를 움직인다. | 접근하거나 공격 위치를 바꿀 필요가 있다. | 사냥을 이어 갈 위치에 도달한다. |
```

현재 표는 번호, 기능명, 기능 설명을 각각 분리한다. 아래 행은 형식을 설명하기
위해 조건과 결과를 축약한 예시다.

```markdown
| Sub-SR | Function name | Function description | Condition | System behavior and result |
|---|---|---|---|---|
| 03 | 사냥 이동 | 몬스터를 사냥할 위치로 캐릭터를 움직인다. | 접근하거나 공격 위치를 바꿀 필요가 있다. | 사냥을 이어 갈 위치에 도달한다. |
```

예시의 `01` → `03`은 표 형식 때문이 아니라 자동사냥 SR 통합에 따른
하위 번호 변경이다. 형식 변경과 ID 변경은 별도로 관리해야 한다.

### 각 열의 역할

| 열 | 작성할 내용 |
|---|---|
| Sub-SR | 상위 SR 안에서 사용하는 두 자리 식별 번호 |
| Function name | 하위 기능을 식별하는 짧은 이름 |
| Function description | 기능의 책임과 범위 |
| Condition | 해당 동작이 발생하는 조건 |
| System behavior and result | 조건이 충족됐을 때의 동작과 관찰 가능한 결과 |
| Verification Criteria | 별도 정량 기준이나 검증 조건이 필요할 때만 추가 |

이 분리는 기능의 책임과 조건별 동작을 구별하게 한다. 기능 설명에는 그 기능이
무엇을 담당하는지 쓰고, 결과에는 해당 조건에서 무엇을 수행하는지 쓴다.
같은 내용을 두 열에 반복하지 않는다. 품질 요구사항에도 같은 열 구조를 적용했다.
현재 품질 표의 `Function name`과 `Function description`에는 품질 항목의 이름과
평가 범위를 적는다.

## 3. 최상위 요구사항의 depth 조정

여기서 depth는 문서 제목의 단계가 아니라 요구사항이 다루는 기능의 크기와
상하 관계를 뜻한다. 최상위 SR은 사용자에게 제공하는 완결된 기능을 설명하고,
Sub-SR은 그 기능에 속하는 의미 있는 동작을 설명한다.

| 기능 | 변경 전 최상위 SR | 변경 후 구조 |
|---|---|---|
| 자동사냥 | SR_01 사냥터 선택·상황 파악, SR_02 이동·공격·물약 사용, SR_03 문제 복귀·중단 | SR_01 자동사냥 아래 8개 Sub-SR |
| 자동 성장 | SR_04 캐릭터 생성, SR_05 사냥터 이동·성장 단계 전환, SR_06 퀘스트, SR_07 장비·스킬·스탯 관리 | SR_04 자동 성장 아래 6개 Sub-SR |
| 다중 PC 모니터링 | SR_08 여러 PC의 실행 상태 확인 | SR_08 다중 PC 모니터링 아래 상태 표시·문제 PC 식별 유지 |

자동 성장의 Overview에는 생성부터 성장까지의 흐름을 설명하고, 사냥터 이동
후에는 SR_01의 자동사냥을 재개한다고 명시했다. 이렇게 하면 자동 성장과
자동사냥의 관계를 설명하면서 사냥 동작을 두 곳에 중복 정의하지 않는다.
퀘스트와 설정 갱신의 구체적인 실행 순서는 출처에서 확정하지 않았으므로
새로 정하지 않았다. 표의 번호만으로 실행 순서를 해석해서도 안 된다.

품질 요구사항인 SR_09의 MVP 사냥 지속성·생존과 SR_10의 장시간 운영 지속성은
별도로 유지했다. 화면 기반 제어와 실행 환경도 System Constraints에 유지했다.
기능의 depth를 맞추기 위해 품질 기준이나 외부 제약까지 기능 아래에 넣지는 않는다.

## 4. ID와 추적 정보 변경

남아 있는 상위 SR의 ID는 유지하고, 통합된 하위 항목에는 새 상위 SR 내 번호를
부여했다. 따라서 상위 ID의 빈 번호는 의도적으로 남아 있다. 기존 ID가 모두
그대로 유지된 것은 아니므로 아래 대응 관계로 이전 참조를 추적한다.

| 이전 Sub-SR | 현재 Sub-SR | 항목 |
|---|---|---|
| SR_01_01 | SR_01_01 | 사냥터 선택 |
| SR_01_02 | SR_01_02 | 사냥 상황 파악 |
| SR_02_01 | SR_01_03 | 사냥 이동 |
| SR_02_02 | SR_01_04 | 주력 공격 |
| SR_02_03 | SR_01_05 | 자원 보충 |
| SR_03_01 | SR_01_06 | 목표 부재 복귀 |
| SR_03_02 | SR_01_07 | 위치 판단 복귀 |
| SR_03_03 | SR_01_08 | 불확실한 상태 중단 |
| SR_04_01 | SR_04_01 | 생성과 플레이 인계 |
| SR_05_01 | SR_04_02 | 목적지 이동 |
| SR_05_02 | SR_04_03 | 성장 단계 전환 |
| SR_06_01 | SR_04_04 | 퀘스트 수행 |
| SR_07_01 | SR_04_05 | 장비 관리 |
| SR_07_02 | SR_04_06 | 스킬·스탯 관리 |

SR_01의 Source UR은 UR_01·UR_02·UR_03으로, SR_04의 Source UR은
UR_07부터 UR_11까지로 통합했다. 각 상위 SR의 Data도 합쳤고, Open Questions의
Related SR 참조를 새 구조로 갱신했다. Sub-SR은 상위 SR의 출처와 상태를 상속한다.

기존 동작, 실행 조건, 검증 수치, `proposed` 상태를 보존했다. MVP와 후속 단계의
범위 구분 및 미확정 UR의 Unused UR Inputs 목록도 유지했다. UR 자체의 내용과
상태는 변경하지 않았다.

## 5. system-astronaut 개선에 반영할 규칙 제안

다음은 이 사례에서 도출한 개선 제안이다. 이 기록 작성으로 스킬 자체가
수정된 것은 아니다.

1. **SR을 만들기 전에 기능 수준을 정한다.** 사용자에게 제공하는 완결된 기능을
   최상위 SR로 정하고, 그 기능에 필요한 동작을 Sub-SR로 배치한다. UR 하나를
   SR 하나로 기계적으로 변환하지 않는다.
2. **최상위 기능끼리 비교한다.** 한 SR은 전체 기능인데 다른 SR은 그와 비슷한
   기능의 일부 단계라면 통합이나 분리가 필요한지 검토한다. 이름이나 표 행 수가
   같다는 이유만으로 depth가 맞는다고 판단하지 않는다.
3. **Sub-SR은 의미 있는 기능이나 동작 단위로 작성한다.** 문장 하나, 검증 항목
   하나마다 ID를 만들지 않는다. 같은 하위 기능의 조건별 분기는 같은 Sub-SR
   ID를 반복해 기록한다.
4. **표의 번호·이름·설명을 분리한다.** 출력 템플릿에 `Sub-SR`, `Function name`,
   `Function description`, `Condition`, `System behavior and result`를 명시한다.
   Verification Criteria는 별도 기준이 필요할 때만 추가한다.
5. **기능 간 관계를 Overview에 설명한다.** 다른 SR의 기능을 이용하는 경우
   참조로 연결하고, 동일한 동작 요구사항을 중복 작성하지 않는다. 출처에 없는
   순서나 정책을 기능 흐름을 설명한다는 이유로 추가하지 않는다.
6. **재구성 시 추적성을 함께 갱신한다.** 유지 가능한 상위 ID는 보존한다.
   부모가 바뀌어 하위 ID를 변경해야 하면 이전→현재 대응표를 남기고,
   출처 UR·Data·Open Questions·관련 문서 참조를 함께 확인한다.
7. **기능·품질·제약을 각각 검토한다.** 기능의 depth를 통일하되 품질 목표와
   외부 제약은 별도의 요구사항 유형으로 유지한다. 품질 표에서 기능 중심의
   열 이름을 그대로 쓸지 여부는 템플릿 개선 시 검토할 수 있다.

## 6. 개선 결과를 검토할 기준

- 최상위 기능 목록만 읽어도 시스템이 제공하는 주요 기능을 파악할 수 있는가?
- 최상위 기능 중 다른 최상위 기능의 일부 단계와 비슷한 크기의 항목이 섞여 있는가?
- 각 Sub-SR의 기능명, 책임, 조건, 결과를 구별해서 읽을 수 있는가?
- 통합 전 동작·예외·검증 기준·확정된 UR의 범위가 빠짐없이 남아 있는가?
- 기능 간 재사용 관계가 명확하고 동일한 동작을 중복 정의하지 않았는가?
- 변경된 ID의 대응 관계가 기록되고 관련 참조가 갱신됐는가?
- 요구사항의 재구성 과정에서 상태를 승인으로 바꾸거나 미확정 정책을 추가하지 않았는가?

이번 요구사항 수정은 문서 내용을 대조하고 `git diff --check`로 공백 오류를
확인했다. 이 검증은 문서 변경에 대한 확인이며 기능 구현이나 게임 실행 시험을
의미하지 않는다.
