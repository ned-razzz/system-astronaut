# UR 작성 원칙과 스킬 개선 요약

UR은 **사용자가 얻으려는 완결된 결과**를 단위로 작성한다. 입력에 나온 동작을 각각 요구사항으로 만들기 전에, 어떤 결과를 함께 완성하는지 판단해야 한다.

## 어떻게 작성해야 하는가

1. **실제 사용자를 식별한다.** 제품의 기능과 가치를 제공받는 사람을 사용자 스토리의 주어로 삼는다. 제품 사용자, 제품 자체, 제품이 조작하는 대상을 구분하고 사용자가 정한 용어를 따른다.
2. **최종 결과를 기준으로 묶는다.** 같은 결과를 완성하는 단계·수단·조건은 하나의 UR에 둔다. 서로 다른 사용자 결과를 독립적으로 제공하면 분리한다. 개별 실행이나 모듈 분리가 가능하다는 이유만으로 나누지 않는다.
3. **스토리에 역할·목표·가치를 쓴다.** 사용자가 무엇을 원하며 왜 필요한지 설명한다. 개발·통합·평가 작업은 그 자체가 제품이 제공하는 기능일 때만 사용자 목표가 된다.
4. **수용 기준에 필요한 세부 결과를 보존한다.** 목표 달성 여부를 관찰할 수 있게 쓰며, 합의한 정량 조건이나 사람의 판단을 사용할 수 있다. 측정하기 쉽다는 이유로 목표를 약한 대리 지표로 바꾸지 않는다. 상세 시험 준비·반복·분석 절차는 수용 조건과 구분한다.
5. **미정인 제품 결정만 질문한다.** 사용자 목표·제품 범위·수용 조건을 `Pending Product Decisions`에 관련 ID와 질문형으로 남긴다. 상세 시스템 동작이나 구현 선택을 UR에서 모두 결정하려 하지 않는다.
6. **기존 문서의 형식과 합의를 유지한다.** 신규 문서는 UR별 한 행의 표를 기본으로 하되 기존 문서의 구조와 열을 우선한다. 명시적 제외는 `Excluded Scope`에 보존한다.

예를 들어 생성·이동·퀘스트·레벨업·스킬 배분은 ‘목표 사냥터에서 사냥할 준비를 마친다’는 결과를 함께 완성한다. 따라서 자동 성장 하나로 묶고 세부 결과를 수용 기준에 담는다. 자동 사냥은 별도로 제공되는 사용자 결과이므로 독립 UR로 유지할 수 있다.

## 작업 로그에서는 어떻게 작성했는가

근거: [UR 지침 검토](../samples/logs/2026-10-02_user_requirements_skill_review.md), [범주화 논의](../samples/logs/2026-10-02_user_requirements_categorization_log.md), [후속 사용자 결정](../samples/logs/2026-10-02_system_requirements_authoring_log.md).

| 작성 과정 | 실제로 정리한 방식 | 도출할 원칙 |
|---|---|---|
| 동작별로 나뉜 요구사항을 다시 묶었다. | 생성·이동·퀘스트·성장을 자동 성장에 모으고, 제품 수준의 다섯 사용자 기능으로 정리했다. | 세부 내용의 누락 방지와 UR 분할은 별개다. 목표를 묶어도 세부 내용은 수용 기준에 남긴다. |
| 사용자와 캐릭터의 의미를 정정했다. | 스토리 주어는 ‘사용자’, 조작 대상은 ‘캐릭터’, 소프트웨어는 ‘프로그램’으로 통일했다. | 도메인 용어를 먼저 확인하고 행위의 주체와 대상을 명시한다. |
| 제작 과정이 섞인 항목을 정리했다. | 연구·평가·외부 기능 통합보다 사용자가 받는 기능과 가치에 집중했다. | 제품 결과와 제품을 만드는 작업을 구분한다. |
| 목표의 의미를 후속 논의에서 바꿨다. | 사람 유사성은 불규칙하고 다양한 키 입력으로, 모니터링은 안정적인 관제와 알림으로 정정했다. | 작성자가 임의로 목표를 약화하지 않되 사용자의 명시적인 변경은 반영한다. |
| 표를 여러 절로 바꾼 뒤 원래 형식으로 복구했다. | 요청하지 않은 요약·ID 대응표·후속 메모를 제거하고 요구사항 표를 유지했다. | 형식 변경과 작업 기록 추가는 내용 수정과 별개다. |

[현재 UR 샘플](../samples/user_requirements.md)은 이 결과를 `ID | name | User story | Acceptance Criteria | State` 표로 표현한다. 다섯 기능이나 ‘사용자·캐릭터·프로그램’이라는 용어 자체를 모든 프로젝트의 규칙으로 만들지는 않는다.

## UR·SR·SA에 공통으로 적용할 원칙

- **합의한 목표와 범위를 보존한다.** 미래 기능이나 어려운 목표를 임의로 축소하지 않는다. 최신 사용자 결정은 적용하고, 해결되지 않은 충돌은 명시한다.
- **단계의 역할을 구분한다.** UR은 사용자 결과, SR은 이를 충족할 시스템 동작·품질·외부 제약, SA는 이를 담당할 구조와 연결을 설명한다.
- **의미 있는 단위로 묶고 필요한 세부 내용은 남긴다.** UR에서는 같은 사용자 결과를 완성하는 항목을 묶는다. 문서를 짧게 만들기 위해 목표나 수용 조건을 삭제하지 않는다.
- **모르는 것은 질문하고 추측으로 채우지 않는다.** 질문은 해당 단계의 결정에 집중한다. UR·SR의 상태는 `proposed`·`confirmed`만 사용하며, 질문이 없다는 사실을 확정이나 구현 완료로 해석하지 않는다.
- **산출물과 작업 보고를 구분하고 추적성을 유지한다.** 기존 형식과 ID를 보존한다. 변경 대응·상태 변경 근거·후속 영향은 응답이나 요청된 로그에 보고하고, 관련 UR→SR→SA 참조는 갱신한다.

## 스킬에 반영할 핵심

[astronaut-ur/SKILL.md](../skills/astronaut-ur/SKILL.md)의 수정은 다음 세 가지에 집중한다.

- `Workflow`: 사용자·용어 확인 → 최종 결과 식별 → 세부 항목 범주화 → 스토리·수용 기준 작성 순서를 명시한다.
- `Principles`: 기존 분할 규칙 앞에 같은 결과의 단계·수단·조건을 묶는 기준을 넣고, 사용자 관점과 목표의 강도 보존을 보강한다.
- `Output and Updates`: 기존 형식 유지 규칙은 그대로 적용하고, ID 대응과 변경 보고를 요구사항 본문에 넣지 않도록 위치를 명확히 한다.
