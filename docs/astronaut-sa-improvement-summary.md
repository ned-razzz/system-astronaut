# SA 작성 원칙과 스킬 개선 요약

SA는 **확정 SR을 어떤 구성요소가 맡고, 어디에서 실행되며, 어떻게 연결되는지** 설명한다. 요구사항의 기능 개수를 그대로 컴포넌트 개수로 바꾸지 않고, 현재 설계에서 필요한 책임과 실행·배치 경계를 표현해야 한다.

## 어떻게 작성해야 하는가

1. **확정 SR과 기존 설계 결정을 읽는다.** 현재 필요한 기능·품질·외부 제약을 확인하고, 사용자가 정한 구성과 미결정 선택을 구분한다. 미확정 SR을 확정 설계의 근거로 사용하지 않는다.
2. **구조도의 목적과 수준을 정한다.** 전체 구성, 프로세스 배치, 내부 모듈, 실행 흐름 중 설명하려는 관심사를 선택한다. 필요한 관점만 작성하며 내부 클래스나 데이터 구조를 미리 확정하지 않는다.
3. **책임과 실제 경계를 기준으로 구성한다.** 기존에 합의한 프로세스 구성을 우선한다. SR 하나마다 서비스·프로세스·클래스를 만들지 않는다. 추가 분해에는 현재 요구사항과 설계 이유가 필요하다.
4. **하드웨어와 소프트웨어 배치를 구분한다.** 물리 호스트 안에 실행 프로세스를 배치하고 원격 연결과 같은 호스트 내부 연결을 구별한다. 대표 인스턴스만 그렸다면 어떤 구성이 반복되는지 설명한다.
5. **연결의 의미를 드러낸다.** 필요한 통신 방향·방식과 교환 정보의 역할을 표시한다. 프로토콜은 요구사항이나 설계 결정의 근거를 확인하고, 미정인 기술은 질문이나 후보로 남긴다.
6. **책임과 출처를 짧게 연결한다.** 그림의 핵심 컴포넌트가 맡는 책임과 관련 SR을 확인할 수 있게 한다. SR 본문을 복사하지 않는다. 보조 도구는 목적과 설계 근거를 밝히고 임의 SR을 출처로 붙이지 않는다.
7. **필요한 생략을 설명한다.** 해당 없는 관점·영역은 `n/a`와 이유를 밝히며 빈 영역을 채우기 위해 장치를 만들지 않는다. 그림과 설명의 명칭·배치·연결을 맞추고 다이어그램이 정상적으로 표현되는지 확인한다.

여러 기능을 한 서비스 프로세스에서 수행하는 설계도 가능하다. 화면 인식·입력·복구가 독립 SR이라는 사실만으로 각각을 별도 프로세스로 분리할 필요는 없다.

## 작업 로그에서는 어떻게 작성했는가

근거: [SA 다이어그램 작성 기록](../samples/logs/2026-10-02_system_architecture_authoring_log.md).

| 작성 과정 | 실제로 정리한 방식 | 도출할 원칙 |
|---|---|---|
| 전체 구조를 Mermaid로 작성했다. | UI·Service·Device 영역을 기준으로 PC 하드웨어 안에 프로세스를 배치했다. | 하드웨어와 소프트웨어 경계를 함께 보여 주되 영역 구성 자체를 공통 템플릿으로 강제하지 않는다. |
| 관제와 실행 기능을 배치했다. | Master PC에는 AdminGUI, Slave PC에는 게임 기능을 수행하는 UhlanageService를 두었다. | 기능 목록보다 실제 실행 위치와 책임을 기준으로 구조를 표현한다. |
| 개발자 모니터를 추가했다. | 사용자 요청에 따라 Slave PC 내부에 DebugMonitor 프로세스를 배치했다. | 기존 결정과 요청된 변경을 반영하되 새로운 제품 기능을 임의로 만들지 않는다. |
| 통신 관계를 표시했다. | 관제–서비스의 원격 연결과 디버그 모니터–서비스의 같은 PC 내부 연결에 양방향 TCP를 표시했다. | 호스트 경계와 연결 방향·방식을 명확히 한다. |
| 여러 실행 PC를 한 대로 대표했다. | 같은 구성을 각 Slave PC에 적용하고 AdminGUI가 각 서비스와 통신한다고 설명했다. | 대표 인스턴스 그림에는 반복 배치의 의미를 보완한다. |
| 사용자의 표현 요청을 반영했다. | 다크 테마를 적용하고 영역·하드웨어·프로세스를 명도 차이로 구분했다. | 시각 표현은 가독성과 사용자 요청을 따르며 특정 테마를 기본 설계 규칙으로 만들지 않는다. |

로그의 강점은 불필요한 기능별 프로세스 분할을 피하고 호스트·프로세스·통신 경계를 간결하게 표현한 점이다. [현재 SA 샘플](../samples/system_architecture.md)은 그림만 있어 SR 출처와 책임, 반복 배치 설명이 드러나지 않는다. 이 부분은 기존 스킬의 추적성 원칙에 맞춰 보완해야 한다.

## UR·SR·SA에 공통으로 적용할 원칙

- **합의한 목표와 범위를 보존한다.** SA는 확정 SR 안에서 구조를 선택한다. 설계를 하면서 제품 기능이나 범위를 바꿔야 한다면 요구사항 결정을 먼저 확인한다.
- **단계의 역할을 구분한다.** UR은 사용자 결과, SR은 시스템 동작·품질·외부 제약, SA는 책임의 배치와 인터페이스를 설명한다. SA에서 SR을 다시 길게 명세하지 않는다.
- **의미 있는 단위로 묶고 필요한 세부 내용은 남긴다.** SA에서는 구조도 수준에 맞는 책임과 실제 실행·배치 경계로 묶는다. 기능 단계마다 계층·프로세스·클래스를 추가하지 않는다.
- **모르는 것은 질문하고 추측으로 채우지 않는다.** 미정인 구조·프로토콜은 질문이나 후보로 표시한다. 별도 장치가 없다는 사실과 PC 하드웨어 전체가 해당 없다는 판단을 구분한다.
- **산출물과 작업 보고를 구분하고 추적성을 유지한다.** 기존 표현과 명칭을 우선하고 핵심 구조의 출처 SR을 남긴다. 테마 변경이나 편집 이력은 구조 설명과 섞지 않는다.

이번 프로젝트의 Master·Slave PC 구성, TCP, 개발자 모니터, 다크 테마는 설계 선택이다. 공통 스킬에는 그 선택을 그대로 복사하기보다 경계·책임·출처를 명확히 표현하는 원칙을 넣는다.

## 스킬에 반영할 핵심

[astronaut-sa/SKILL.md](../skills/astronaut-sa/SKILL.md)의 수정은 다음 세 가지에 집중한다.

- `Workflow` 추가: 확정 SR·기존 결정 확인 → 구조도 수준 선택 → 책임·배치·연결 작성 → 출처·범위 검토 순서를 명시한다.
- `Principles`: SR과 컴포넌트를 일대일로 대응시키지 않는 기준, 하드웨어·프로세스 경계와 반복 배치의 표현을 보강한다.
- `Output`과 검토 기준: 그림에서도 책임·관련 SR·필요한 생략을 확인할 수 있게 하고, 명칭·연결·미결정 선택을 점검한다. 모든 관점이나 보조 문서를 기본 생성하지 않는다.
