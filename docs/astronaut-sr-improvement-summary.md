# SR 작성 원칙과 스킬 개선 요약

SR은 **확정된 사용자 목표를 충족하기 위해 시스템이 어떻게 동작해야 하는지** 설명한다. UR의 기능 이름을 그대로 옮기기보다 실제 수행 흐름을 풀고, 공통 책임을 정리한 뒤 의미 있는 기능과 Sub-SR로 작성해야 한다.

## 어떻게 작성해야 하는가

1. **현재 합의에서 출발한다.** `confirmed` UR의 스토리와 수용 기준, 최신 사용자 결정과 명시된 외부 제약을 읽는다. 과거 문서의 세부 범위나 더 강한 의미를 임의로 되살리지 않는다.
2. **표를 쓰기 전에 수행 흐름을 푼다.** 시작 조건 → 진행 단계 → 결과 확인 → 반복·전환 → 종료와 예외 대응을 정리한다. 기능 이름이나 개별 입력 동작만 나열하지 않는다.
3. **반복되는 공통 책임을 추출한다.** 여러 기능에 같은 동작이 있고 독립적으로 설명 가능한 책임이면 별도 SR로 묶는다. 기존 기능의 중복은 줄이되 목적지 도착·작업 완료·다음 활동 전환 같은 업무 결과는 남긴다.
4. **Sub-SR에는 조건·행동·결과를 연결한다.** 언제 무엇을 수행하고 결과에 따라 어떻게 진행하는지 명세한다. 실패 시 허용된 복구, 성공 후 재개와 복구 불가 시 중단을 필요한 범위에서 설명한다.
5. **동작·품질·검증·설계를 구분한다.** 프로그램이 구매 성공이나 작업 완료를 확인하는 것은 기능이다. 시험 준비·반복·증거 수집은 검증 계획, 도구·라이브러리·저장 방식 선택은 설계다. 합의한 품질 목표를 검증 절차와 함께 삭제하지 않는다.
6. **명세를 완성하는 데 필요한 결정만 질문한다.** 시스템 동작·품질 기준·외부 제약의 미정을 `Pending System Specification Decisions`에 관련 ID와 질문형으로 남긴다. 알려진 동작은 먼저 작성하고 수치나 정책을 추측하지 않는다.
7. **출처·상태·형식을 함께 관리한다.** 기능·품질 SR은 출처 UR에, 외부 제약은 그 외부 근거에 연결한다. 새 SR은 기본 `proposed`이며 출처 UR의 확정이 SR의 확정을 뜻하지 않는다. 기존 표와 ID, 사용자가 정한 우선순위 부여 방식을 따른다.

‘물약을 관리한다’는 설명만으로는 동작을 알기 어렵다. ‘물약이 부족하면 사냥을 멈추고 상점으로 이동해 구매한 뒤, 구매 결과를 확인하고 기존 사냥터로 복귀한다’처럼 흐름을 연결해야 필요한 동작과 예외를 도출할 수 있다.

## 작업 로그에서는 어떻게 작성했는가

근거: [SR 작성·수정 과정](../samples/logs/2026-10-02_system_requirements_authoring_log.md), [미결정 질문의 역할 구분](../samples/logs/2026-10-02_pending_requirements_decisions_log.md).

| 작성 과정 | 실제로 정리한 방식 | 도출할 원칙 |
|---|---|---|
| 다섯 사용자 기능으로 초안을 작성했다. | 이후 사냥·성장의 시작·진행·반복·중단을 구체화했다. | UR의 기능 이름에서 바로 표로 넘어가지 않고 수행 흐름을 먼저 분석한다. |
| 사냥과 성장의 동작이 중복됐다. | 화면 인식·입력 조작·복구를 독립 SR로 추출했다. | 공통 책임은 한곳에 명세하고 각 업무 흐름에 필요한 결과는 보존한다. |
| 성장에서 사냥을 사용하는 관계를 정리했다. | 자동 사냥과 자동 성장은 별도 SR로 유지하고, 성장 중 사냥을 수행한다고 설명했다. | 다른 기능을 사용한다는 이유만으로 반드시 합치지 않는다. |
| 물약 사용에서 보충·복귀로 동작이 확장됐다. | 부족 감지 → 상점 이동 → 설정된 물약 구매 → 결과 확인 → 사냥터 복귀를 명세했다. 위치·경로·상점 정보의 필요성도 도출했다. | 흐름을 완성하는 데 필요한 동작은 도출하되 지도 보유 방식 같은 구현 선택은 설계에 남긴다. |
| 검증 내용이 기능 본문을 차지했다. | 사용자 요청에 따라 24시간 무개입 시험, 입력 패턴 비교와 관제 검증 내용을 별도 계획으로 옮겼다. | 검증 가능성과 검증 절차를 같은 것으로 보지 않는다. 프로그램의 결과 확인은 SR에 남긴다. |
| SR 간 연결 문장이 반복됐다. | 당연한 연결 설명은 제거하고 Source UR와 필요한 업무 관계는 유지했다. | 출처 추적은 보존하되 의미를 추가하지 않는 참조 문장은 줄인다. |
| 미정 사항을 동작 중심으로 인터뷰했다. | 물약 보충·기존 캐릭터에서 성장 시작·복구 범위·응답 실패 처리·알림 대상을 결정했다. | 현재 기능의 동작을 정하는 질문에 집중하고 구현·시험 결정을 섞지 않는다. |
| 앞선 결정을 사용자가 수정했다. | 처치 수 목표는 보류하고 현재 중단 조건에서 제거했다. 합의된 수정은 관련 SR과 참조에 반영했다. | 최신 결정을 초안 전체에 적용한다. 보류를 확정 기능이나 영구 제외로 해석하지 않는다. |

[현재 SR 샘플](../samples/system_requirements.md)은 기능별 Overview·State·Priority·Source UR와 Sub-SR 표를 사용한다. 이 양식은 유지할 수 있지만, 모든 프로젝트에 같은 열이나 기능 목록을 강제할 필요는 없다.

## UR·SR·SA에 공통으로 적용할 원칙

- **합의한 목표와 범위를 보존한다.** SR은 UR의 수용 기준까지 도출 범위에 포함한다. 사용자 변경 없이 목표를 축소하거나 새 기능·정책을 추가하지 않는다.
- **단계의 역할을 구분한다.** 사용자 결과는 UR, 시스템의 의무 동작·품질·외부 제약은 SR, 구현 구조·기술 선택은 SA에서 다룬다. 시험 절차는 필요한 검증 문서에서 다룬다.
- **의미 있는 단위로 묶고 필요한 세부 내용은 남긴다.** SR에서는 일관된 기능과 공통 책임을 묶는다. 이 분해 결과를 곧바로 프로세스·클래스 구조로 확정하지 않는다.
- **모르는 것은 질문하고 추측으로 채우지 않는다.** 결정 대상을 먼저 분류하고, 이미 답한 질문은 반복하지 않는다. UR·SR의 상태는 `proposed`·`confirmed`만 사용하며 질문 유무·우선순위·구현 완료와 구분한다.
- **산출물과 작업 보고를 구분하고 추적성을 유지한다.** 기존 형식·ID를 보존하고 재구성 시 허가된 문서 범위의 참조를 함께 갱신한다. 작업 이력을 기능 본문에 누적하지 않는다.

이번 프로젝트의 ‘검증 기준 분리’와 ‘우선순위는 명시된 경우만 기록’은 사용자 결정이다. 일반 스킬에서는 필요한 Verification Criteria와 근거 있는 Priority를 허용하되 사용자 양식을 우선한다. 검증 내용을 다른 문서로 옮겼다면 관련 SR 연결과 목표의 보존도 확인해야 한다.

## 스킬에 반영할 핵심

[astronaut-sr/SKILL.md](../skills/astronaut-sr/SKILL.md)의 수정은 다음 세 가지에 집중한다.

- `Workflow`: 현재 합의 확인 → 수행 흐름 분석 → 공통 책임 추출 → Sub-SR 작성 → 누락·중복·미결정 검토 순서를 명시한다.
- `Derivation Principles`: 공통 책임 추출, 업무 결과 보존, 런타임 결과 확인과 외부 시험의 구분, 필요한 기능 관계만 참조하는 기준을 보강한다.
- `Decisions and State`: 질문 전에 제품·시스템·설계·검증 결정을 분류하고 최신 답변을 관련 명세에 적용하도록 한다. 이미 반영 지시를 받은 결정에 추가 승인 단계를 만들지 않는다.
