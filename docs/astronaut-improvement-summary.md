# Astronaut 스킬 개선 통합 요약

세 스킬의 개선 방향은 **합의한 사용자 목표를 보존하면서, 각 단계에 필요한 판단과 세부 내용을 명확히 하는 것**이다. UR은 사용자가 얻을 결과를 정리하고, SR은 그 결과를 충족할 시스템 동작을 명세하며, SA는 이를 담당할 구성요소와 연결을 설계한다.

이 문서는 UR·SR·SA 개선 요약과 후속 사용자 결정을 통합한 작성·검토 기준이다. 실제 반영 여부는 각 `SKILL.md`에서 확인한다. 산출물은 각 단계의 명세와 기본 ID 추적성에 집중하고, 보조 문서의 기본 생성은 요구하지 않는다.

## 1. 전체 흐름과 단계별 역할

```text
프로젝트 설명 → 사용자 요구사항(UR) → 시스템 요구사항(SR) → 시스템 아키텍처(SA)
```

| 단계 | 핵심 질문 | 정리 단위 | 다음 단계로 전달할 내용 |
|---|---|---|---|
| UR | 사용자는 어떤 결과를 얻고, 왜 필요한가? | 완결된 사용자 결과 | 사용자 스토리, 수용 기준, 제품 범위 |
| SR | 그 결과를 충족하려면 시스템이 어떻게 동작해야 하는가? | 일관된 기능과 공통 책임 | 동작·품질·외부 제약, 출처 UR 또는 외부 근거 |
| SA | 어떤 구성요소가 책임을 맡고, 어디에서 어떻게 연결되는가? | 책임과 실행·배치 경계 | 다이어그램과 SR 전체의 기능 흐름을 반영한 설계 요약 |

UR의 기능 수가 SR이나 SA의 구성요소 수를 결정하지 않는다. 하나의 사용자 결과에 여러 시스템 책임이 필요할 수 있고, 여러 책임을 하나의 프로세스가 수행할 수도 있다.

## 2. 공통 개선 원칙

- **현재 합의와 목표의 강도를 보존한다.** 최신 사용자 결정을 관련 항목 전체에 반영한다. 어려운 목표를 임의로 축소하거나, 과거의 범위를 되살리거나, 새 기능·정책을 추가하지 않는다. 명시적으로 제외한 제품 목표는 `Excluded Scope`에 남기고, 보류를 영구 제외로 해석하지 않는다.
- **각 단계의 결정을 구분한다.** 사용자 결과는 UR, 시스템 동작·품질·외부 제약은 SR, 구현 구조·기술 선택은 SA에서 다룬다. 상세 시험 준비·반복·분석은 검증 계획에 둔다. 검증 절차를 옮겨도 합의한 품질 목표와 관련 요구사항 연결은 보존한다.
- **의미 있는 단위로 묶되 세부 내용을 잃지 않는다.** UR은 같은 결과를 완성하는 단계·수단·조건을 묶고, SR은 반복되는 공통 책임을 추출하며, SA는 실제 실행·배치 경계를 표현한다. 문서를 줄이기 위해 수용 조건이나 업무 결과를 삭제하지 않는다.
- **입력 전체의 확정 후 다음 단계로 진행한다.** 각 스킬은 원천 입력의 모든 항목이 확정되었는지 먼저 확인한다. `proposed`이거나 상태가 없거나 불명확한 항목이 하나라도 있으면 전체 작성을 중단하고 해당 문서와 항목을 알린다. 상태 없는 프로젝트 설명이나 외부 입력은 전체 항목을 포괄하는 명시적 사용자 확인이 필요하다. 확정된 항목만 골라 부분 산출물을 만들거나 입력을 자동 확정하지 않는다. 참고 예시와 검토·수정·확정 대상 산출물 자체는 원천 입력으로 취급하지 않는다. 이후 수정 가능성과 별개로 단계 진입 시 입력을 완성해 오류 전파를 줄인다.
- **미정 사항은 해당 단계의 질문으로 남긴다.** 입력 확정 검사를 통과한 뒤 현재 단계에서 알려진 내용을 작성하고, 미정인 수치·정책·기술은 추측하지 않는다. 제품·시스템·설계·검증 중 어떤 결정인지 구분해 관련 ID나 구성요소와 짧은 질문을 남긴다. 이미 답한 질문이나 반영을 지시받은 결정에 추가 승인 단계를 만들지 않는다. 해결되지 않은 충돌은 명시한다.
- **출처·상태·형식을 유지한다.** UR → SR의 출처 ID 연결과 외부 제약의 근거를 보존한다. SA는 구성요소 식별용 ID를 유지하되 SR ID 연결이나 대응표를 요구하지 않는다. UR·SR의 상태는 `proposed`와 `confirmed`만 사용하며, 질문 유무·우선순위·구현 완료와 구분한다. 기존 문서의 구조·ID·열과 사용자 지정 방식을 우선한다.
- **문서화를 최소화한다.** 명세, 필요한 질문·충돌, 기본 ID 연결만 남긴다. SA의 설계 근거는 다이어그램 아래 짧은 요약에 담는다. 작업 기록·변경 이력·검토 보고서·별도 추적성 표·검증 계획 등 보조 문서는 요청받았을 때만 작성한다. 해당 없는 영역은 생략하고 `n/a`나 생략 이유 목록을 기본 생성하지 않는다.

## 3. 단계별 작성 방식과 스킬 개선 항목

### UR: 동작 목록을 완결된 사용자 결과로 정리한다

**작성 순서:** 실제 사용자와 용어 확인 → 최종 결과 식별 → 세부 항목 묶기 → 스토리·수용 기준 작성 → 미정 제품 결정 확인.

제품 사용자, 제품 자체, 조작 대상을 구분하고 스토리에 역할·목표·가치를 쓴다. 같은 결과를 완성하는 동작은 하나의 UR에 두고, 독립적으로 제공되는 사용자 결과는 분리한다. 개발·통합·평가는 그 자체가 제품 기능일 때만 사용자 목표로 다룬다.

수용 기준에는 목표 달성을 관찰할 수 있는 세부 결과를 남긴다. 합의한 정량 조건이나 사람의 판단을 사용할 수 있으며, 측정하기 쉽다는 이유로 목표를 약한 대리 지표로 바꾸지 않는다. 미정인 사용자 목표·범위·수용 조건은 `Pending Product Decisions`에 관련 ID와 질문으로 기록한다.

예를 들어 캐릭터 생성·이동·퀘스트·레벨업·스킬 배분이 함께 ‘목표 사냥터에서 사냥할 준비를 마친다’는 결과를 만든다면 자동 성장 UR로 묶는다. 각 동작의 필요한 결과는 수용 기준에 남기고, 별도로 제공되는 자동 사냥은 독립 UR로 유지할 수 있다.

**스킬 반영:** `Workflow`에 입력 확정 검사와 결과 중심 작성 순서를 넣고, `Principles`에 묶기 기준과 목표 강도 보존을 보강한다. `Output and Updates`에는 기존 형식 유지와 명세 본문에서 작업 기록·변경 이력을 제외하는 원칙을 명확히 한다.

### SR: 수행 흐름을 분석하고 공통 책임을 추출한다

**작성 순서:** 확정 UR·최신 결정·외부 제약 확인 → 수행 흐름 분석 → 공통 책임 추출 → Sub-SR 작성 → 누락·중복·미정 사항 검토.

UR의 기능 이름을 곧바로 표로 옮기지 않고, 시작 조건 → 진행 → 결과 확인 → 반복·전환 → 종료·예외 대응을 먼저 정리한다. Sub-SR에는 조건·행동·결과를 연결하고, 필요한 범위에서 허용된 복구와 성공 후 재개, 복구 불가 시 중단을 설명한다. 공통 책임을 추출해도 목적지 도착·작업 완료·다음 활동 전환 같은 업무 결과는 각 흐름에 남긴다.

예를 들어 물약 관리는 ‘부족 감지 → 사냥 중단 → 상점 이동 → 구매 → 구매 결과 확인 → 기존 사냥터 복귀’로 풀어야 필요한 동작을 도출할 수 있다. 프로그램의 구매 결과 확인은 기능이며, 구매 시험의 반복·증거 수집은 검증 계획이다. 지도 저장 방식은 설계 결정으로 남긴다.

미정인 시스템 동작·품질 기준·외부 제약은 `Pending System Specification Decisions`에 관련 ID와 질문으로 기록한다. 기능·품질 SR은 출처 UR에, 외부 제약은 외부 근거에 연결한다. 새 SR은 기본 `proposed`이며, 출처 UR의 확정이 SR의 확정을 뜻하지 않는다.

기존 우선순위와 사용자 지정 척도는 유지한다. 우선순위가 없는 SR은 AI가 사용자 목표에 대한 기여, 기능 간 의존성, 실패 영향을 바탕으로 초안을 설정하고 사용자가 검토·수정한다. 기존 척도가 없으면 High / Medium / Low를 사용한다. AI가 설정한 값은 같은 메타데이터 항목에 제안임과 짧은 근거를 표시한다. 우선순위는 범위 제외·구현 순서·요구사항 확정 상태와 구분하며 필수 제약을 약화하지 않는다.

**스킬 반영:** `Workflow`에 흐름 분석과 공통 책임 추출을 넣고, `Derivation Principles`에 업무 결과 보존과 실행 중 결과 확인·외부 시험의 구분을 보강한다. `Decisions and State`에는 결정 분류와 최신 답변의 일관된 반영을 명시한다. `Traceability and Priority`와 기본 출력에는 AI의 우선순위 초안 설정과 사용자 검토를 반영한다.

### SA: 책임과 실제 실행·배치 경계를 표현한다

**작성 순서:** 입력 SR 전체의 확정·기존 설계 결정 확인 → 하드웨어 식별 → 소프트웨어 책임·배치·연결 작성 → 설계 요약 작성 → SR 전체의 기능 흐름·품질·제약과 그림·요약의 일치 검토.

미확정 SR을 확정 설계의 근거로 사용하지 않는다. 전체 구성·프로세스 배치·내부 모듈·실행 흐름 중 필요한 관점만 선택하고, 합의한 프로세스 구성을 우선한다. SR마다 서비스·프로세스·클래스를 만들지 않으며, 추가 분해에는 현재 요구사항과 설계 이유가 필요하다.

물리 호스트 안에 실행 프로세스를 배치하고 원격 연결과 같은 호스트 내부 연결을 구별한다. 연결에는 필요한 방향·방식·교환 정보의 역할을 표시한다. 대표 인스턴스만 그렸다면 반복 배치의 의미를 설명하고, 미정인 프로토콜은 질문이나 후보로 남긴다.

다이어그램 바로 아래에 짧은 설계 요약을 작성한다. SR 전체를 충족하는 데 필요한 하드웨어, 소프트웨어 구성요소의 책임 분할·배치 이유, 구성요소가 협력하는 기능 흐름을 설명한다. 관련 결과 확인·전환·복구·종료와 품질·외부 제약을 구조가 어떻게 지원하는지 확인할 수 있게 한다. SR 명세를 반복하거나 SR ID를 나열한 대응표를 만들지 않는다. 설계 제안과 실제 구현·검증 완료를 구분하고, 모호한 SR 동작은 질문으로 남긴다.

보조 도구의 목적과 설계 근거도 필요한 경우 이 요약에 담는다. 해당 없는 영역은 생략하고 `n/a`나 생략 이유 목록은 요구하지 않는다. 그림과 요약의 명칭·배치·연결 및 다이어그램의 정상 표시를 확인한다.

**스킬 반영:** `Workflow`에 하드웨어·소프트웨어·통신 구성 순서를 두고, `Design Principles`에 SR과 구성요소의 일대일 대응 방지 및 호스트·프로세스·반복 배치 표현을 보강한다. `Output`에는 다이어그램 아래 설계 요약을 넣고, `Review`에서는 SR ID 대응 대신 SR 전체의 기능 흐름·품질·제약을 종합적으로 검토한다. 모든 관점이나 보조 문서를 기본 생성하지 않는다.

## 4. 작업 사례에서 확인한 보완점

| 사례 | 통합 문서에 남길 교훈 |
|---|---|
| UR의 동작별 분할을 자동 성장 중심으로 재정리하고 사용자·캐릭터·프로그램의 의미를 정정했다. | 사용자와 최종 결과를 먼저 식별하고 세부 내용은 수용 기준에 보존한다. |
| SR에서 화면 인식·입력·복구를 공통 책임으로 추출하고 물약 보충·복귀 흐름을 구체화했다. | 중복을 줄이면서 시작부터 결과·전환·예외까지 흐름을 완성한다. |
| 검증 절차를 분리하고 처치 수 목표의 보류 등 후속 결정을 반영했다. | 기능·품질 목표와 시험 절차를 구분하고 최신 결정을 관련 항목 전체에 적용한다. |
| SA에서 호스트·프로세스·통신 경계를 간결하게 표현했다. | 기능별 프로세스 분할을 피하고 실제 배치를 보여 준다. 다이어그램 아래 요약에서 필요한 하드웨어, 책임 분할, 기능 흐름, 반복 배치의 의미를 설명한다. |

다섯 사용자 기능, 특정 도메인 용어, 검증 기준의 별도 문서화, Master·Slave PC, TCP, 개발자 모니터, 다크 테마는 해당 프로젝트의 결정이다. 공통 스킬에는 이 선택 자체를 강제하지 않고, 사용자 양식을 우선하며 목표·책임·경계와 필요한 출처를 명확히 한다. 우선순위는 후속 결정에 따라 AI가 초안을 설정하고 사용자가 검토·수정한다. 필요한 수용·품질 기준은 명세에 보존하되 별도 검증 문서는 요청받았을 때만 작성한다.
